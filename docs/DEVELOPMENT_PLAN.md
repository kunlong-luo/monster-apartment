# 《怪物租客公寓》独立游戏开发计划书

**项目代号：** MONAP　|　**当前版本：** V0.1.1　|　**计划日期：** 2026-10-20　|　**负责人：** 独立开发者　|　**方向：** Web 优先，PC 后续评估

## 1. 项目摘要 / 经营目标

使用 Pagevela 风格的 React + TypeScript + Vite + Tailwind + Zustand 工程体系，以及 Phaser 4 游戏渲染来开发一个能免费试玩的 2D 经营/布局策略游戏。玩家不是只点按钮获取金币，而是通过住户与房间的相邻组合获得可解释的策略反馈。首版不追求美术量产；只验证 **布局是否有趣、决策是否有意义、玩家是否愿意重玩**。

**成功定义：** 14 天内形成可试玩原型；30 天内让至少 10 位真实玩家体验；60 天内依据反馈做出继续/调整/停止结论；90 天内有一个经过验证的更完整 Web Demo，或及时终止该方案。时间只是目标，不是保证。

**商业边界：** 90 天内不把游戏广告和 Steam 销售当作可靠现金流。已有的 React/TS 开发服务仍单独作为短期现金流尝试；不要为了游戏采购电脑或付费上架。

## 2. 用户与卖点

- 核心玩家：喜欢布局、房间管理、轻策略，以及不断尝试组合的 PC/Web 玩家。
- 游戏一句话：招募怪物当租客，布置六间房的特殊组合，度过五天夜晚考核。
- 15 秒卖点：调换两间房，组合加成瞬间改变；夜晚事件检验经营策略。
- 假设（尚未验证）：怪物题材 + 邻接组合的经营规则能产生比普通租金点击玩法更丰富的决策。
- 不把视觉题材当作市场验证证据，必须研究竞品与真人反馈。

## 3. V0.1 可交付范围

### 必须包含

1. 三层楼，每层两间房，总计六间房。
2. 四种租客：史莱姆、火精灵、幽灵、石像鬼，各有入住价格、租金和事件作用。
3. 点击选择房间、招募入住、移动或交换住户。
4. 每日租金、每位住户维护费、邻接组合加减成。
5. 固定的五天事件循环（方便测试）；金币与满意度变动。
6. 结果结算、经营日志、胜负条件与重新开始。
7. 不依赖云服务的免费本地试玩；基础桌面浏览器布局。
8. 规则测试和项目管理文件。

### 明确不做

多人、注册登录、排行榜、联网同步、随机地图、20+ 租客、正式音乐美术、云存档、移动 App、Steam SDK、广告 SDK、支付系统、付费营销。

### V0.1 验收标准

- 进入页面能看到六间房和四种可选住户。
- 新招募的住户正确扣除金币，已入住的房间不允许重复招募，金币不足时给出提示。
- 调换位置后相邻组合加成可预测地改变。
- 每次结算都记录租金、维护费、相邻加成、夜间事件的净收入。
- 结算到第 5 天出现成功或未达标结果；不能继续结算，能重开。
- 刷新后重新开始是首版已知限制（不是 bug）。

## 4. 游戏核心机制

**一天内的行动：** 观察现金与满意度 → 在空房招募或搬家 → 查看相邻加成 → 结束当天 → 触发事件 → 下一天。支持自由尝试布局，不按真实时间等待。

**经济公式：**

`当日净金币 = Σ(租客基础租金) + 相邻组合收益 - 3 × 已入住人数 + 当日事件金币`。

**相邻：** 上下/左右共享一条边的房间。对角线不算；每对只计算一次。

| 组合 | 金币/天 | 满意度/天 | 设计意图 |
|---|---:|---:|---|
| 史莱姆 + 火精灵 | +3 | 0 | 蒸汽供能 |
| 幽灵 + 石像鬼 | +4 | 0 | 夜间守护 |
| 史莱姆 + 石像鬼 | +2 | 0 | 清洁协作 |
| 火精灵 + 幽灵 | -3 | -4 | 冷热争执 |

**初始值：** 35 金币，满意度 70。五天结束时需要达到至少 135 金币、至少 55 满意度。

以上数值是可调试草案，不是已验证的最终平衡。

## 5. 技术架构与文件管理

**技术基线已升级（2026-10-20）：** 参考 Pagevela，但不复制 PDF/Markdown 等无关功能。Node 24、pnpm 12.13.0、React 19.3.1、TypeScript 7.0.2、Vite 8.3.4、Tailwind CSS 4.3.3、Zustand 5.0.15、Phaser 4.2.1；质量工具为 Vitest 5.0.4、Playwright 1.64.1、ESLint 10.12.0。具体版本策略与安装步骤见 `docs/TECH_STACK_PAGEVELA.md`。

**重要验收状态：** 6 项核心规则 Node 测试已通过，但新版 React/Phaser/TypeScript 工程尚未联网安装依赖、运行 `pnpm build` 和 Playwright，需要在用户 Pop!_OS + Node 24 环境验收；此处不能认定新版已完整可运行。


- `src/core/engine.js`：无 DOM/Phaser 依赖的确定性规则，使用 TypeScript 类型声明文件描述接口；同时被试玩页和正式工程使用。
- `src/game/ApartmentScene.ts`：Phaser 渲染六个房间和选择状态。
- `src/App.tsx`：React 面板；通过 `src/store/useGameStore.ts`（Zustand）管理 UI 状态、经营命令与核心规则交互。
- `src/components/GameBoard.tsx`：React 与 Phaser 的事件桥接。
- `preview/`：无 npm 依赖的离线部署预览界面；项目根目录 `playable.html` 是可以直接双击运行的单文件构建，由 `scripts/build_standalone.py` 自动从共享规则源码生成。两者都不等同于最终 Phaser 运行时。
- `tests/`：无依赖的 Node 单元测试，新增 Vitest 测试；`e2e/`：Playwright 冒烟测试。
- `docs/CHANGELOG.md`：版本记录；`management/TASKS.csv`：任务管理表。

**版本命名：** `V主版本.功能版本.补丁版本`。新增机制升次版本（0.2）；纯修复升补丁版本（0.1.1）；保留明确的发布说明。

**分支策略：** `main` 保持可试玩，功能在 `feature/<task-id>` 完成，合并前至少检查规则测试和启动。

## 6. 14 天原型里程碑

| 时间 | 主要任务 | 可验收产物 |
|---|---|---|
| D1–D2 | 初始化项目、六间房点击选择 | Web 画面可交互 |
| D3–D4 | 四种住户、招募、搬家/交换 | 房间布局可以改变 |
| D5–D6 | 收租、维护费、邻接收益 | 经营数值有反馈 |
| D7–D8 | 五种夜间事件与胜负结果 | 能玩完一个五天回合 |
| D9–D10 | 基础 UI、日志、错误提示、重新开始 | 不需要作者解释即可游玩 |
| D11–D12 | 规则测试、平衡审查、修 bug | 无严重阻断问题 |
| D13–D14 | 浏览器试玩和第一轮反馈 | 至少 5 位真实测试者的反馈 |

**V0.1.1 当前交付说明：** 核心规则和免依赖试玩仍为 V0.1；React+Phaser 4、Pagevela 风格新技术工程升级源码已经制作，但此环境无法联网安装 npm 第三方包，`pnpm install/typecheck/build/e2e` 待用户在本地完成。

## 7. 30/60/90 天经营计划

| 阶段 | 目标 | 明确的关口 |
|---|---|---|
| D1–D30 | 提升游戏可读性、制作英文界面；获取 ≥10 次实际试玩 | 玩家能否独立理解并完成一局？ |
| D31–D60 | 调整机制，目标 ≥20–30 次有效试玩；做第一个短视频 | 主要玩家是否主动尝试不同布局？ |
| D61–D90 | 选“继续做 Steam 完整版 / Web 平台合作 / 停止项目” | 是否存在足够清晰的核心乐趣和可见的玩家需求？ |

**决策规则：** 连续两轮测试中，大多数玩家都无法理解规则 → 先调整引导；能理解但没有重玩意愿 → 修改核心玩法；体验很好但内容制作太贵 → 缩小规模；不要被沉没成本绑架。

## 8. 海外验证与宣发

1. 先在自有页面提供免费试玩链接，邀请有模拟经营习惯的海外玩家测试，不购买流量。
2. 用游戏内真实操作录制 10–20 秒视频，展示“一个房间位置改变带来不同收益”的机制。
3. 与社区交流时先阅读规则，不进行无差别营销。不能以点赞数量替代实际试玩完成率。
4. 收集少量自愿反馈：哪里没看懂、哪里最好玩、是否愿意再玩；不需要采集敏感信息。
5. 没有完成玩法验证前不签不理解的独占协议，不承诺广告分成或 Steam 销量。

## 9. 发行与盈利路径

- **Web：** 静态发布/itch.io 先免费试玩；平台分发及广告合作需要另行审核，收入不保证。
- **PC/Steam：** 只有当玩法验证通过，再考虑 Electron 桌面打包、Windows 真机测试、商店资产、Steam Direct 费用与平台协议。
- **手机：** 暂时不做原生 iOS/Android App；触控适配在后期根据用户反馈评估。
- **现金流：** 三个月内希望争取收入应优先独立探索 React/TS 小型开发服务，不能把本游戏收入计入保底。

## 10. 风险清单

| 风险 | 触发信号 | 对策 |
|---|---|---|
| 核心不好玩 | 玩一局后没有再次尝试欲望 | 只修改规则，不加美术 |
| 内容规模失控 | 任务积压、缺少完整可玩版本 | 冻结新增玩法，优先打通一局 |
| Web 平台无流量 | 发链接后少有玩家试玩 | 优先改善展示素材与目标玩家匹配 |
| 技术迁移成本 | Electron/Steam 功能超出预期 | 核心数值与 UI/平台代码分离 |
| 数值不平衡 | 有一种固定布局总是最佳解 | 记录胜率，调整组合收益和事件 |
| 现金流紧张 | 未产生收入却持续加支出 | 禁止为未经验证的产品付费发行或买量 |
| 审核/合同要求 | 发布平台存在账户和签约门槛 | 先确认资格和条款，必要时在监护人协助下合法合规进行 |

## 11. 复盘与任务管理

每周一次：更新 `management/TASKS.csv`；标记 `TODO / DOING / BLOCKED / DONE`；把问题写入 `management/ISSUES.md`；每次发布写 `docs/CHANGELOG.md`。下周任务控制在 3–5 个，不同时开发多款未验证游戏。

**每周回顾问题：** 这周新增了什么可玩的内容？核心玩法更有趣了吗？遇到的最大阻碍是什么？有没有实际玩家反馈？是否需要停止一项工作？
