## 参与者和分组

招募至少 **10 名非作者、首次接触**《怪物公寓》的玩家（PC 与手机均应覆盖）。仅用 `T01` 等匿名编号；每人 15–20 分钟；记录设备类别、视口、浏览器与有无触摸。体验前说明可随时停止，不收集姓名、账号、联系方式、屏幕录像或个人存档。

## 主持流程（不解释按钮意义）

1. **0–3 分钟 · 首次发现：** 从大厅进入游戏，记录是否自行找到工坊、路线是否清晰、第一次困惑的 UI 位置。
2. **3–12 分钟 · 实际经营：** 只提示目标「尝试让工坊能够持续生产，并完成第一个委托」。观察能否无提示进行派工、开启自动生产、**单独**开启自动履约、理解截止日期与库存变化；注意不要把生产开关与履约开关混为一谈。
3. **12–16 分钟 · 问题与迁移：** 观察返回大厅、进入订单或仓库、刷新后是否找得回进度。不能强制要求受测者在短时间完成真实倒计时；未完成时记录原因及经过时间，不把它算作操作失败。
4. **16–20 分钟 · 访谈：** 问「你觉得下一步要做什么？」「最有意思/最困惑的一个瞬间是什么？」「明天愿意再玩吗？为什么？」避免暗示正确答案。

仅在玩家卡住至少 60 秒、并明显无法继续时允许一次标准提示：「可以看看工坊里其他可交互位置」。在结果表写明何时求助；**受提示后成功不得计入无提示成功率**。

## 计分口径与决策

用同目录的 `r113-first-session-results.template.csv` 复制生成实际匿名结果文件，保留空字段表示未观察，不要猜测填入 `false`。布尔值统一使用 `true` / `false`；`would_replay` 为 `yes` / `no` / `unsure`。

- 观察工坊进入率：`entered_workshop=true` / 有效受测总数。
- 自主派工、自动生产、显式履约发现率：各字段 `true` / 该字段有明确观察结果的人数；对设备分别汇总。
- 首单完成率：`completed_first_order=true` / 实际具备足够测试时间的参与者人数；记录等待时间限制。
- 卡点：按照 `major_blocker` 的可复现页面/操作汇总最高频 3 项。每条需附复现路径、影响设备、预期与实际，不以个人偏好代替证据。
- 重玩意愿：分别计 `yes` / `no` / `unsure`，不能当成真实次日留存率。

结束后由负责人出具一页 **R12 决策记录**：先优化新手引导、深化自动经营反馈、修复导航/性能，还是进入正式人物/机器美术量产。每项结论附原始匿名样本数和真实观察。未招满 10 人、规则未保护或结果尚无证据时，只标记**待验证**。


## 匿名观察工具（不替代真实招募）

- [PR #22](https://github.com/kunlong-luo/monster-apartment/pull/22) 已合并且 [Pages 在正式游戏 SHA 上成功部署](https://github.com/kunlong-luo/monster-apartment/actions/runs/43551776453)：主持人可用 `/research/first-session/` 的**独立匿名观察记录页**；完整地址为 `https://kunlong-luo.github.io/monster-apartment/research/first-session/`。它不在七个游戏场景入口中，也没有存储玩家观察数据的后端。
- 一位玩家对应一份 CSV。主持人输入 `T01`、`T02` 等匿名编号、设备与真实观察结果，点「生成单人 CSV」后应**下载文件**并自行保管；页面重载不会恢复未导出的观察数据。需要将 10 份记录按同一表头合并进工作表（保留一行表头），不可将空记录或自动化跑测填成真实人次。
- 这个页面不上传、不持久化**观察数据**，不能提供自动远程汇总、后台通知或玩家招募。主持人应优先使用自己的独立设备记录，避免在受测玩家的游戏设备上切换路由而影响观察与游戏自动进程。
- 主持人记录资料时不输入真实姓名、联系方式、账号、个人存档或未经许可的图像。若参与者中途退出，记录其退出原因（匿名）和实际分钟数，但不算已完成 15–20 分钟的有效访谈。

## 招募和执行准备（计划，不是已经获得参与者）

- 建议邀请 **5 名 PC + 5 名手机** 玩家，以便两端均有样本；这只是招募配额，不是统计显著性声明。每名玩家需独立首次接触游戏、使用自己的非敏感化匿名编号，不要用作者或自动化脚本充数。
- 由主持人单独邀请并取得同意；不把潜在参与者的真实姓名、联系方式、浏览器存档或未经许可的截图写入 GitHub 公开仓库。玩家拒绝或中断应尊重，不计为已完成 15–20 分钟测试。
- 预约前检查：[Issue #9](https://github.com/kunlong-luo/monster-apartment/issues/9) 需要仓库管理员实际设置并由 API 复核；发布入口必须可访问；如最近有游戏代码更改，核对功能 SHA 的 full/Quality/Visual/Pages 证据，不用旧 SHA 的报告冒认新功能版本。
- 试玩时复用 `r113-first-session-results.template.csv`，第一行表头不变；真实受测者产生的数据单独保存、按事先许可处理，公开汇总应只保留匿名信息。记录空白字段表示未观察，不等同于失败。
- 建议把 **进入工坊、派工、自动生产、自动履约、首单** 各步骤对应的“首次发现时间”和阻碍简写到 `notes`，并对提示前/提示后行为明确区分。不能以主持人代点计算无提示成功。

### 可直接发送的招募邀请（文本模板）

> 我们正在测试一款免费网页游戏《怪物公寓》的首次上手体验，邀请从未玩过的朋友独立试玩 15–20 分钟。测试会观察你如何寻找工坊、开启自动生产和处理委托；不需要游戏经验，也没有“答错”。你可以随时停止。只记录匿名操作与体验反馈，不要求提供姓名、账号或个人存档，也不会未经同意录屏。如果愿意参与，我会提供正式试玩链接并约定时间。

### 主持人开始前的统一口径

> 今天主要观察游戏是不是容易理解，而不是考核你。请像平时一样操作；我会尽量不提示。如果出现困惑，可以告诉我你的想法。你可以随时结束，不需要提供个人信息。

### 试玩结束后的交付证据

- 汇总有效参与者数量、PC/手机覆盖、各项观察字段的 **已观察分母**；以匿名记录为依据，明确统计口径及无法按时等待首单的情况。
- 给出影响最大的 3 个可复现障碍（页面/操作、设备、影响人数、复现方式）；再评估是否应优先做新手引导、导航、生产反馈或者美术。不要因为场景截图不够漂亮就推定它是主要留存障碍。
- 当真实样本不足 10 人，保持 [Issue #10](https://github.com/kunlong-luo/monster-apartment/issues/10) open，注明“尚未完成”；**不生成或补填虚构玩家结果**。
